Locations, Permits & The Scout Book

@@CH11@@

A location is the one department where the production is a guest. Somebody else owns the room, somebody else's neighbours have to tolerate the truck, and a city office decides whether the street is yours at all. The Scout Book at /locations/ is where that becomes a record: what you saw, who you have to ask, and what time the light goes.

How this chapter was written. By reading the files, not by using the screens. Cinamate is still being built; wherever this page and the running software disagree, believe the software and treat the paragraph below as stale.

The location bible

The page is locations/index.html; its arithmetic and its directories are locations/lib-scout.js, which exports CScout. Everything typed on the page is written to one localStorage key, SB_ScoutBook_v1, on every change — there is no save button. That object holds the locations, the hub picked in each directory, the last sun query and the checklist ticks.

A location record is built by blankLocation(). No field is mandatory, and an empty one stays empty rather than being guessed at.

The hospital fields are not decoration. The call-sheet builder in producer/schedule-board.js reads SB_ScoutBook_v1 for the hospital, parking and load-in lines of the safety block, and today/index.html matches the day's sets loosely against location names to surface the nearest hospital on the day view. A blank hospital field prints as a stated gap on the sheet.

Note that the platform holds two location registers: this one, and a flatter SB_Locations_v1 table on the Production page (production/production.js) with a permit-expiry chip. They do not synchronise. The Scout Book is the one carrying the hospital, the pin and the photographs.

Suggesting locations from the screenplay

⟳ Suggest from script reads SB_Timeline_v1 in this browser and runs scriptLocations() over its scriptText. That function takes every slugline — INT, EXT, INT/EXT, I/E, with or without a leading scene number — strips the prefix and the time-of-day suffix at the first spaced dash, upper-cases what remains, and groups repeats. An unreadable slugline becomes (UNNAMED LOCATION) rather than disappearing.

One caution: the scene numbers it reports are positional. It counts sluglines from the top of the file and ignores any number printed in the script, so a scene the screenplay calls 12 will be listed as the third slugline if it is the third slugline. On an unnumbered draft the two agree; on a revised, numbered script they will not. Nothing is added to the book until you press + Add to book on a suggestion.

Scout photographs

Adding a photo re-encodes it in the browser before storage: the longest edge is reduced to 1280 pixels if it exceeds that, and the result is written as a JPEG data URL at quality 0.85. The bytes go to IndexedDB — database cinamate_scout, object store photos, keyed by a generated id of the form ph<timestamp><random>. Only the id is written into the location record. This is why a location can carry photographs that are not on the machine you are reading: the record and the image travel separately.

When they have separated, the page says so. A photo id whose bytes are not in this browser is replaced by a dashed ⚠ photo missing tile naming the id, and the strip gains one line telling you to restore the production from a backup that carries media. An earlier version deleted the element instead, which made a scout book that had lost every image look like one that had never been photographed.

Scout photographs are other people's property, and they travel. These are interiors of real premises — very often private homes whose owners let a location manager through the door, not a studio. The bytes sit in IndexedDB unencrypted; they are packed into a .cinamate export, which is a self-contained file with no size limit; and netlify/functions/projects-sync.js lists cinamate_scout/photos among the three stores the studio cloud accepts, which means a push puts them where all five owners of the shared cloud can pull them down. Cloud transfer is capped — 900 KB per record, 1 MB per request, 48 requests, so 48 MB per production — but that is a size limit, not an access limit. Treat a scout book as commercially and personally sensitive, know where its exports are going, and say so to the people whose homes are in it.
Deleting a location deletes its photographs. The ✕ on a location card asks for confirmation and then removes every photo id it owns from IndexedDB as well as the record itself. The per-photo ✕ deletes those bytes immediately with no confirmation at all. Neither is undoable from this page; the only recovery is a restore, and only if the backup was taken with media.

The tech-scout checklist

locationChecklist() returns ten fixed items — power, parking, load-in, bathrooms, neighbors, noise, cell signal, nearest hospital, permits and insurance COI — each with a sentence about what to actually record. The power item insists on amps per leg and a phase count rather than a reassurance, because the load calculator needs a number.

The ticks are stored in SB_ScoutBook_v1 under checks, keyed by item id. That is one set of ten for the whole production, not one per location — ticking Noise does not record that noise was checked anywhere in particular. Use it as a scout-day aide-mémoire and put the findings in the location's own fields.

Power on a location

Each card carries a supply-versus-order panel. parseSupply() will read a number back out of the scouted power note — it understands forms like 100A, 200 amp 3-phase and 2 x 20A — and returns nothing at all when the note has no number in it, because an unparseable note is an unknown supply and not a zero. powerDemand() then puts a fixture order against it: nameplate watts, with HMI ballasts drawn at 1.2× the lamp rating, converted to amps per leg at 120V and divided across three legs when the service is three-phase. The verdict is one of ok, tight, derate, over or unknown, against the 80% continuous-load ceiling. An unrecorded supply returns unknown and still shows the draw, so the gap is visible rather than assumed adequate. Inrush on an HMI strike is higher than any of these figures and is not modelled.

The permit directory

CScout.PERMITS holds six hubs. Each entry carries the office name, when a permit is required, cost, lead time, insurance, police and traffic extras, an applyUrl, and a verified flag. The rule the data obeys — and scripts/test_locations.mjs asserts it — is that an unverified entry may never carry an application URL; the page then renders a web-search link instead of an Apply button. All six entries in the file today are marked verified and all six carry an official application URL.

Hubs are matched by matchHub(), which is deliberately loose: it takes an alias table (la, nyc, hollywood, burbank, brooklyn, queens, burnaby, gta), then matches if the hub name appears anywhere in your text, or if four or more characters you typed are a prefix of a hub name. That means free text such as shooting in downtown toronto, ON resolves correctly — and equally that a place that merely contains a hub name will resolve to that hub. Read the card's heading before you trust the fees on it. Use Advisor location takes the jurisdiction picked for tax incentives out of SB_Budget_v1 and maps it through INCENTIVE_HUB: Ontario to Toronto, BC to Vancouver, Georgia to Atlanta, California to Los Angeles, New York to New York, and either UK incentive to London. Anywhere outside those six, the page says so and tells you to find the local film office yourself.

Log permit fee commits an amount to the Money Room as an open purchase order against account 13000 (Locations), vendor Film permit office, written into SB_Money_v1. It is a real commitment in the budget, made from this page, and it must be reversed in the Money Room rather than here.

The directory text is truncated, and one footnote contradicts the card above it. In every one of the six permit entries the required field ends mid-sentence — several end mid-word — and other fields do the same; the page prints them verbatim, so an operator reads a rule that stops before its exception. Separately, the card's footnote states that this build could not verify fees or application URLs and that none are shown, while the card directly above it shows both. The file's own header comment is likewise missing a clause. Nothing in this directory is a quote or a legal position: confirm the fee, the lead time and the insurance wording on the office's own page before you rely on any of it.

The stage and facility directory

CScout.STAGES covers the same six hubs, six facilities each, with a booking paragraph per hub. A facility entry carries a name, a kind, a qualitative description of its stages, a notable line, an optional website and a verified flag; an unverified facility carries no website by rule, and the page renders a search link in place of the site button. Three of the thirty-six entries are unverified today — two in Toronto, one in Vancouver — and one verified entry has no website recorded, which also produces a search link.

The stage descriptions are abbreviated the same way the permit fields are: counts and square footages frequently break off mid-figure, and the booking paragraphs, which carry contact routes for some operators, break off mid-address. Where an entry looks incomplete, it is incomplete — do not read the missing half as absent detail. The consistent finding across all six booking notes is that the professional tier does not publish rates: every one of these markets is direct quote, negotiated with the facility's own bookings team. The page carries that as a standing caution, and it is the honest part of the directory.

Sun times, and the timezone that decides them

Section 4 of the page computes daylight for a pin. Pick a location from the dropdown to copy its latitude, longitude and recorded offset into the bar, or type them; supply a date, and press Compute. The maths is tools/lib-sun.js (TSun), the tested NOAA/Meeus implementation described in Chapter 19, accurate to about two minutes. An approximate second solar engine that once lived in lib-scout.js has been deleted, and scripts/test_locations.mjs asserts its absence so it cannot come back.

You get sunrise, the end of morning golden hour, the start of evening golden hour, sunset, civil dusk and total daylight hours; below them the compass bearing the sun rises and sets on, and solar noon with the sun's altitude. Azimuth is degrees clockwise from true north. At high latitudes where the sun does not cross the horizon, the panel says midnight sun or polar night rather than printing a time.

The clock is yours to supply. The code will not guess it. sunTimes() returns UTC instants; fmtLocal(ms, offsetMinutes) renders them in whatever offset it is given, and given none it uses the offset of the machine you are reading on. The Scout Book therefore uses, in order: the number in the UTC offset (min) box, or the tzOffsetMin recorded on the location, or — failing both — tzOffsetFromLon(), which is round(lon / 15) hours. That last is solar mean time. It knows nothing of political borders and nothing of daylight saving, so it can be a full hour wrong; the panel marks it ESTIMATED whenever it is used, and that label is the one thing to read before publishing a call time. Enter the location's real civil offset in minutes — -420 for Los Angeles in August, 330 for a half-hour zone — and it is stored on the record with tzSource set to entered. Note that nothing on this page fills that field in for you: the code comments describe the offset arriving from the forecast service, but the only writer of tzOffsetMin on a location record is you typing it. The scale of the error is in scripts/test_sun.mjs, which pins an LA sunset at 19:28 in the location's own offset and 02:28 in UTC, and re-runs its assertions in child processes forced to three different machine timezones.

Weather, and what leaves the device

TSun.weatherUrl() builds a request to https://api.open-meteo.com/v1/forecast. What it sends is the location's latitude and longitude, a start and end date, a fixed list of daily variables — weather code, maximum and minimum temperature, maximum precipitation probability, maximum 10 m wind speed — and timezone=auto. No key, no account, no production name; the call is made by your browser directly to that host, which is why https://api.open-meteo.com appears in the connect-src directive of _headers. A coordinate pair for a private house is still a disclosure, and it is worth knowing you are making it.

Be precise about where that happens, because it is not this page. The Scout Book loads lib-sun.js but never calls weatherUrl: its sun panel is pure local arithmetic and makes no network request. The forecast lives in the Producer Suite — the day planner in tools/sched-weather.js, loaded only on /producer/, and the call-sheet forecast line — and both read their pin from SB_ShootPlan_v1, which is a separate coordinate you enter there. Those screens also capture utc_offset_seconds from the reply and keep it as the plan's real civil offset; the Scout Book's own records never receive it.

shootRisk() scores a forecast day out of 100 for reordering exteriors, and wmoLabel() names the weather code or reports Code n when it does not recognise one. A failed or blocked request is reported as a failure on the page — it is not permitted to look like a clear day, and not permitted to look like a date beyond the forecast window.
